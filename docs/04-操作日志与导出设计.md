# 04 - 操作日志与导出设计

> **文档状态**：Draft 0.4  
> **上级文档**：[00-项目管理服务设计文档索引](./00-项目管理服务设计文档.md)

---

## 1. 设计目标

操作日志不是报表附属功能，而是项目管理主链路的一部分。第一版必须保证：

1. 任务创建、任务删除、任务状态修改必写日志。
2. 所有逻辑删除必写日志。
3. 日志写入和业务变更必须在同一个数据库事务内提交。
4. 业务成功但日志缺失，视为失败设计。
5. 操作日志支持导出。
6. 导出内容不脱敏。
7. 导出动作本身也要写操作日志或安全日志。

---

## 2. 必须记录的操作

| 领域 | 操作 |
|---|---|
| 项目 | 创建、修改、归档、恢复、逻辑删除 |
| 项目成员 | 添加、角色变更、移除/撤销 |
| 项目部门授权 | 添加、变更、移除/撤销 |
| 任务/子任务 | 创建、标题/描述/负责人/优先级/截止日期变更、逻辑删除、恢复 |
| 状态 | 状态流转、拖拽排序、批量状态修改 |
| 里程碑 | 创建、变更、达成、逻辑删除 |
| 依赖 | 添加、解除 |
| 评论 | 创建、编辑、逻辑删除 |
| 导出 | 项目日志导出、任务日志导出、管理员全局日志导出 |
| 认证安全 | 登录、登出、刷新失败、密码修改、强制下线 |

## 3. 操作日志表

### `operation_logs`

- `id uuid primary key`
- `project_id uuid null references projects(id)`：认证类或全局操作可为空
- `task_id uuid null references tasks(id)`
- `entity_type varchar(64) not null`：`project | task | subtask | member | department_grant | milestone | comment | auth | export`
- `entity_id uuid null`
- `actor_id uuid not null references users(id)`
- `action varchar(64) not null`：例如 `task_created | task_deleted | task_status_changed | logs_exported`
- `before jsonb null`
- `after jsonb null`
- `request_id varchar(80) not null`
- `ip inet null`
- `user_agent text null`
- `created_at timestamptz not null`

规则：

- 日志只追加，不提供普通业务 API 修改或删除。
- 日志清理只能走独立的保留周期和管理员维护流程。
- `before/after` 保存业务变更前后的关键字段。
- 删除操作的 `after` 至少包含 `deleted_at/deleted_by/delete_reason` 或 `revoked_at`。
- 导出不脱敏，因此 `before/after` 会按原始 JSON 输出。

---

## 4. 导出范围

第一版支持三类导出：

| 导出 | 接口 | 权限 |
|---|---|---|
| 项目日志导出 | `GET /api/v1/projects/{project_key}/logs/export` | 超级管理员、项目负责人 |
| 任务日志导出 | `GET /api/v1/tasks/{task_key}/logs/export` | 超级管理员、项目负责人 |
| 全局日志导出 | `GET /api/v1/admin/operation-logs/export` | 仅超级管理员 |

项目成员和观察者可以按权限查看日志，但默认不能导出。原因是导出不脱敏，必须减少批量泄露面。

---

## 5. 导出格式

支持两种格式：

```text
format=csv
format=jsonl
```

建议默认 CSV，排查问题时使用 JSONL。

导出字段：

- `created_at`
- `request_id`
- `project_key`
- `task_key`
- `entity_type`
- `entity_id`
- `actor_account`
- `actor_display_name`
- `action`
- `before`
- `after`
- `ip`
- `user_agent`

不做脱敏：账号、显示名、IP、User-Agent、before/after JSON 原样导出。由于不脱敏，导出必须：

1. 鉴权。
2. 记录导出操作。
3. 限制单次导出时间范围。
4. 使用流式响应，避免一次性加载大量日志到内存。

---

## 6. 查询与索引

推荐索引：

```text
operation_logs (project_id, created_at desc)
operation_logs (task_id, created_at desc) where task_id is not null
operation_logs (actor_id, created_at desc)
operation_logs (entity_type, entity_id, created_at desc)
operation_logs (created_at desc)
```

列表查询必须分页。导出必须要求时间范围，例如默认最近 30 天，最大 180 天；超过范围要求用户缩小条件。

---

## 7. 事务示例

任务状态变更：

```text
begin transaction
  lock task row / check version
  check project permission
  check target status
  update tasks.status_id, completed_at, version
  insert operation_logs(action = task_status_changed)
commit
```

如果 `insert operation_logs` 失败，任务状态变更必须回滚。

## 8. 当前代码实现基线（2026-08-30）

当前已经实现：

- 项目日志、任务日志的分页查询。
- 项目日志、任务日志和超级管理员全局日志的 CSV 导出。
- 导出内容不脱敏，`diff`、`snapshot` 和操作人 UUID 按原始数据写入 CSV，并正确处理逗号、双引号和换行。
- 项目/任务导出只允许超级管理员或项目负责人；全局导出只允许超级管理员。
- 导出完成后追加一条 `audit` 模块日志，记录导出类型、CSV 格式、是否脱敏和导出行数。
- 导出查询按 5,000 条一批读取，避免数据库查询本身一次性加载全部日志。

当前限制：HTTP 响应仍会在服务端内存中组装完整 CSV，尚未改成真正的流式响应；时间范围参数和最大导出时间窗口也尚未接入。生产上线前应优先补齐这两项，以应对大规模全局日志导出。
