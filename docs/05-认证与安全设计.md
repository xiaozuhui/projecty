# 05 - 认证与安全设计

## 1. 认证方式

第一版采用本地账号、密码登录和 JWT 鉴权：

- 登录字段：`account + password`。
- 邮箱不是登录强绑定字段，只作为资料或找回密码扩展。
- 密码只保存 hash，不保存明文。
- 推荐使用 Argon2id 或同等级密码哈希算法。
- JWT secret/private key 通过环境变量或 secret manager 注入，不写入仓库。

---

## 2. Token 策略

| Token | 用途 | 建议 |
|---|---|---|
| Access JWT | 调用 API | 15–30 分钟短有效期，`Authorization: Bearer <token>` |
| Refresh JWT | 刷新 access token | 7–30 天，放 `HttpOnly + Secure + SameSite=Lax` cookie |

Access JWT 不落库。Refresh JWT 只保存 `jti_hash`，支持登出、轮换、撤销和强制下线。

---

## 3. Refresh Token 表

### `jwt_refresh_tokens`

- `id uuid primary key`
- `user_id uuid not null references users(id)`
- `jti_hash text not null unique`
- `expires_at timestamptz not null`
- `revoked_at timestamptz null`
- `created_at timestamptz not null`
- `last_used_at timestamptz null`

---

## 4. Web 安全边界

1. Web 端不建议把长期 token 放入 `localStorage`。
2. 推荐 access token 只保存在内存中，refresh token 放 HttpOnly cookie。
3. 当前前后端采用独立端口部署；生产环境需要明确配置 CORS 来源，JWT refresh 方案应优先采用安全的 HttpOnly cookie 或后续统一网关方案。
4. 如果部署必须纯 Bearer，则缩短有效期并加强 XSS 防护。
5. 内部错误不向浏览器泄露 SQL、密码 hash、token 或堆栈。
6. 登录、登出、刷新失败、密码修改、强制下线写安全日志。

---

## 5. 超级管理员

`users.system_role = super_admin` 是系统最高权限：

- 可以查看所有部门信息。
- 可以查看和管理所有项目、任务、子任务、成员、授权和里程碑。
- 可以查看和导出全局操作日志。
- 仍然要写操作日志，不能因为是超级管理员就绕过审计。

---

## 6. 授权落点

推荐三层防线：

1. **HTTP 层**：校验 JWT，提取当前用户。
2. **Application policy 层**：对每个用例执行资源授权和字段级限制。
3. **Database 层**：外键、唯一、check、事务保证数据完整性。

第一版不启用 PostgreSQL RLS。若未来转为多租户或强隔离部署，再单独做 RLS PoC。
