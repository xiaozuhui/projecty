## 1. 部署拓扑

仓库代码与运行容器保持同样的边界：前端、后端、数据库分别维护，最终由 Docker Compose 和 Nginx 组成同源入口。`backend.Dockerfile` 只编译 Rust API 与 migration，`frontend.Dockerfile` 只编译 SvelteKit；不会把前后端源码混到同一个业务目录。

```text
Browser
   │ HTTPS
   ▼
Reverse Proxy / TLS termination
   ├── /        -> SvelteKit web server
   └── /api/    -> Axum API
                         │
                         ▼
                    PostgreSQL
```

建议同源部署，减少 CORS、JWT refresh cookie 和 CSRF 复杂度：

- `https://projecty.example.com/`：SvelteKit。
- `https://projecty.example.com/api/v1/...`：反向代理到 Axum。
- 生产数据库不暴露公网。
- Axum 提供 `/healthz`，后续再补充存活与就绪两个独立探针。
- 日志输出 JSON，包含 `request_id`、用户 ID、部门 ID、项目 ID、路由、状态码和耗时。
- 密钥通过环境变量或 secret manager 注入。

## 2. 后端测试

1. 领域单测：状态机、子任务两层限制、依赖环检测、任务编号、日期规则。
2. 权限测试：超级管理员、父部门查看下级部门、部门授权、跨部门项目成员、最后负责人约束。
3. 应用层测试：项目归档、任务变更、逻辑删除、任务删除日志、状态变更日志、冲突处理。
4. repository/integration：真实 PostgreSQL migration、约束、分页、事务回滚。
5. HTTP contract：状态码、DTO、错误 envelope、JWT、refresh cookie。
6. 并发 PoC：并发创建任务、并发删除任务、并发拖拽、并发完成任务。
7. 日志导出测试：权限、时间范围、CSV、JSONL、流式响应、大结果集。

## 3. 前端测试

1. UI 组件测试：按钮、表单、弹窗、抽屉、表格、状态标签。
2. 页面测试：部门目录、项目列表、看板、列表、任务详情、成员设置、日志导出。
3. 交互测试：筛选 URL 同步、浏览器返回、拖拽失败恢复、键盘移动任务。
4. E2E：登录 -> 创建项目 -> 加成员 -> 建任务 -> 建子任务 -> 拖到进行中 -> 删除任务 -> 查看项目操作日志 -> 导出日志。
5. 响应式截图：1280×800、1024×768、768×1024、390×844。

## 4. 验收标准

- 超级管理员可以查看所有部门、项目、任务和操作日志。
- 父部门用户可以查看所有下级部门信息。
- 未授权用户无法通过手工构造 API 请求读取或修改不属于自己的项目任务。
- 项目归档后普通项目成员不能继续修改任务。
- 子任务不能再创建子任务。
- 所有删除都是逻辑删除，数据库保留删除人、删除时间和原因。
- 项目成员创建任务、删除任务、修改任务状态后，必须能在项目日志和任务日志中看到对应记录。
- 日志写入和业务变更要么同时成功，要么同时回滚。
- 项目负责人可以导出自己负责项目的操作日志。
- 超级管理员可以导出全局操作日志。
- 日志导出不脱敏，并且导出动作本身有记录。
- 用户属于多个部门时，项目有效角色按直接项目成员和部门授权取最高角色。
- 跨部门用户加入项目后能访问该项目，但不会因此获得其原部门之外的其他项目权限。
- 任务编号在并发创建下不重复。
- 版本冲突不覆盖他人修改，并向用户提供刷新/合并路径。
- 移动端不出现整页横向溢出；看板仅在看板容器内横向滚动。
- 不加载 Tailwind CSS，不使用 Inter/Intel One/Roboto 主字体，不依赖外部 CDN 才能渲染核心界面。

## 5. 分阶段实现计划

### 阶段 0：基础骨架与关键 PoC

- 建立 `backend` 后端、`frontend` 前端的清晰仓库边界；Rust workspace 仅包含 `backend`、`backend/entity` 和 `backend/migrations`，业务模块全部位于 `backend/src`，不拆成独立业务 crate。
- 建立 Docker 多阶段构建文件：Backend 和 Frontend 分开构建，Nginx 与 PostgreSQL 通过 Compose 组合部署。
- 完成数据库 schema v1：用户、部门、用户部门、项目、项目成员、部门授权、状态、任务、子任务、操作日志、JWT refresh token。
- 做任务编号并发 PoC。
- 做 Axum JWT + policy 骨架。
- 做父部门查看下级部门和超级管理员全局查看的权限测试。
- 做任务逻辑删除、子任务两层限制、操作日志事务一致性测试。
- 做操作日志导出 PoC。
- 做 AppShell、项目路由树、设计 tokens。
- 验证同源反向代理、JWT Bearer、refresh cookie 行为。

退出条件：本地可创建用户、部门、项目、任务、子任务；JWT、权限、任务编号、逻辑删除、操作日志和导出有自动化测试；四个目标 viewport 有首轮截图。

### 阶段 1：核心项目管理

- 项目目录和项目概览。
- 看板、列表、任务详情。
- 创建/编辑/逻辑删除任务和子任务。
- 负责人、优先级、标签、截止日期。
- 状态拖拽与乐观并发控制。
- 项目成员与角色。
- 操作日志时间线和导出。

### 阶段 2：计划与协作

- 里程碑。
- 任务依赖和阻塞提示。
- 时间线和日历。
- 评论与站内通知。
- 批量操作和保存的筛选视图。

### 阶段 3：增强能力

- SSE 实时刷新。
- 附件对象存储。
- 项目模板和部门模板。
- 业务数据导入/导出（不含第一版操作日志导出）。
- 可选企业目录同步。
- 可选 PostgreSQL RLS 强隔离方案。

## 6. 关键风险与待验证问题

| 风险/问题 | 当前决策 | 验证动作 |
|---|---|---|
| 部门层级权限是否过度复杂 | 父部门可查看下级部门信息；项目任务权限仍按项目角色 | 写多部门、父子部门、跨部门成员测试 |
| 超级管理员范围 | `super_admin` 全局可见和管理 | 写全局查看、管理、导出测试 |
| 项目成员删除任务 | 允许删除，但逻辑删除并强制写日志 | 验证删除后列表不可见、日志可查、负责人可恢复 |
| 子任务复杂度 | 只允许两层 | 验证子任务不能再创建子任务 |
| 日志导出不脱敏 | 按要求不脱敏，但限制导出权限 | 验证普通成员不能导出、导出动作被记录 |
| 任务编号实现 | 项目行锁计数器 vs per-project sequence | 并发压测后决定 |
| 1,000,000 任务量 | PostgreSQL + Rust 可支撑，但 API/UI 必须分页和索引 | 阶段 0 造数并跑 EXPLAIN、接口耗时和首屏验证 |
| 是否需要实时协作 | 第一版刷新/局部失效，阶段 3 SSE | 统计多人同时编辑频率后决定 |
| 邮件通知 | 第一版关闭 | 若未来开启，先设计 outbox、失败重试和死信处理 |

## 7. SeaORM Migration 目录说明

`backend/migrations` 就是 SeaORM migrations 包，不承载业务服务代码。其 `src` 目录采用 SeaORM CLI 的标准组织方式：`m202...rs` 是实际的版本化迁移文件，`src/lib.rs` 只是把这些迁移注册到 `MigratorTrait`，`src/main.rs` 提供 SeaORM CLI 入口。因此这里的 `lib.rs` 不是额外的业务 `mod` 层，也不会替代实际 migration 文件。
